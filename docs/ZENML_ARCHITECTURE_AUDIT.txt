================================================================================
ARCHITECTURE UNDERSTANDING
================================================================================

**What is ZenML?**
ZenML is an MLOps orchestration framework that manages pipeline execution.
It coordinates steps, handles data flow, and tracks experiments.

**Two Deployment Modes:**

1. **DOCKER MODE** (Standard for production Linux servers)
   - Each step runs in its own Docker container
   - ZenML creates containers automatically
   - Requires Docker installed and running
   - Common in cloud/Linux environments

2. **LOCAL MODE** (Your current setup - CORRECT for Windows + Conda)
   - Each step runs in its own conda environment  
   - ZenML orchestrates via 'conda run' commands
   - NO Docker required
   - Perfect for Windows development with heavy ML models

**Your Implementation:**
You're using ZenML Local Mode with Conda isolation via the CLI step runner.
This is a STANDARD, SUPPORTED, and RECOMMENDED approach for your use case.

================================================================================
WHY THIS ARCHITECTURE EXISTS
================================================================================

**The Problem:**
Different ML models require conflicting dependencies:
- PyTorch vs TensorFlow versions
- CUDA toolkit versions
- Python package conflicts
- Different Python versions (3.9 vs 3.10 vs 3.11)

**Your Solution (CORRECT):**
- ZenML pipeline in goodq_zenml environment (orchestrator only)
- Each step has its own isolated conda environment
- Steps communicate via JSON files (temporary)
- conda_runner.py bridges ZenML → Step environments

**Why Not Docker:**
- Windows Docker Desktop has licensing/performance issues
- Conda already handles environment isolation
- Your ML models are huge (70GB+) - conda caching is faster
- Local development is easier with conda activate
